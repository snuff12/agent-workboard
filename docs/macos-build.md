# Building the macOS app and native widget

The minimum target is macOS 14. The app/service manage local work; WidgetKit reads service-generated JSON only. Widgets neither access SQLite nor execute plugins.

## Command Line Tools build

Requires Rust/Cargo and Swift from Apple Command Line Tools, not Python, agent-memory, or a Google account.

```sh
scripts/build-macos.sh
open "dist/Agent Workboard.app"
```

The bundle contains the SwiftUI app, Rust CLI/service, and actual WidgetKit extension. Default builds use release configuration and local ad-hoc signing. `--debug` selects debug, `--skip-rust` reuses Rust executables, and `--without-widget` is an app-development option rather than the default distribution.

Command Line Tools lacks App Intents metadata processing. That path builds separate native current/upcoming/review widgets. Full Xcode provides configurable views and accents in one widget. Neither path substitutes a small app window for a native widget. The icon is generated by repository AppKit drawing code. Core bundles exclude `plugins/` implementations and dedicated dependencies.

## Local installation and CLI

```sh
scripts/install-local.sh
open "$HOME/Applications/Agent Workboard.app"
"$HOME/.local/bin/workboard" --help
```

Copy to `~/Applications` and link CLI/service into `~/.local/bin`. Add that directory to PATH. Do not overwrite existing regular executables. Override locations with `--destination DIR` and `--bin-dir DIR`. Open the app once, then use macOS **Edit Widgets** to add Agent Workboard.

`--skip-register` skips LaunchServices in isolated tests; ordinary installation registers task deep links. The CLI works with the window closed. To start at login:

```sh
scripts/install-local.sh --start-service
launchctl print "gui/$(id -u)/local.agentworkboard.service"
```

This registers a current-user LaunchAgent, not a system service. `ProcessType=Standard` keeps the service responsive to CLI/app requests. Requests over two seconds and delayed accept-loop wakeups are logged to `~/Library/Logs/AgentWorkboard/service-error.log`. This is development registration; release SMAppService status/consent management is separate work.

The installer holds exclusive `install.lock`; CLI automatic startup obtains a shared lock before launching, preventing an old service from racing an update. Manual-service takeover validates a single PID holding the chosen `service.lock` and exact socket, its UID, and a product-managed executable. Send SIGTERM only to the verified process and wait for lock/socket release. Do not stop services at other paths. Existing LaunchAgents must match app, data, and socket configuration.

Stage a complete app copy and verify signatures before replacement, including same-source/destination installs. Failures before attempting new service startup restore the previous app, links, LaunchAgent, and service. Once startup has been attempted, the service may already have migrated SQLite or accepted new writes: retain the new app, links, LaunchAgent, and database together. Preserve the previous app and installation files in the reported recovery directory. Retry registration, or recover access with the new executable when registration fails and no verified writer exists. Report health without converting the failed installation into success; rerun with the same options to finish. Never automatically downgrade the executable or restore an older database after this boundary. Verify the new service directly through the socket and doctor without CLI autostart. KeepAlive retries use a 30-second throttle.

Disable automatic startup while preserving app/data:

```sh
scripts/uninstall-local-service.sh
```

## Full Xcode project

`macos/project.yml` is the target configuration source. Generation was verified with XcodeGen 2.46.0. Regenerate after adding Swift sources.

```sh
xcodegen generate --spec macos/project.yml
open macos/AgentWorkboard.xcodeproj
```

Choose `WorkboardApp` and the actual Mac. Use the same development team for app and extension.

| Component | Development identifier |
| --- | --- |
| App | `local.agentworkboard.app` |
| Widget | `local.agentworkboard.app.widgets` |
| App Group | `group.local.agentworkboard.shared` |
| Task link | `workboard://task/<TASK_ID>` |

External distribution requires team-owned bundle/group identifiers and any required profiles. Verify signed group entitlements and actual container access on the target Mac; ad-hoc signature success is insufficient.

App/widget read `WorkboardAppGroupIdentifier` from Info.plist. Build staging puts the same value into both plists and app/service/widget entitlements without editing original templates.

```sh
# Requires an installed development-team certificate.
scripts/build-macos.sh --sign "Apple Development: NAME (TEAMID)" --team ACTUALTEAM
# A registered group. identifier can be supplied with an approved profile.
scripts/build-macos.sh --sign "Apple Development: NAME (TEAMID)" --app-group group.example.workboard.shared
```

Replace `ACTUALTEAM` with the actual 10-character uppercase/digit Team ID. `--team` creates `TEAMID.local.agentworkboard.shared` and checks it against the code signature. It cannot be combined with ad-hoc signing. `--app-group` supplies an identifier; it does not grant permission or create a team. The certificate-free default uses `group.local.agentworkboard.shared` and reports access separately.

Apple recommends `group.<name>` plus an authorizing provisioning profile for new code. macOS-specific `TEAMID.<name>` is also supported and permits automatic container access when the signed team matches the prefix. A `group.` profile must be embedded in app/widget; a standalone service needs an App ID and app-like wrapper to use one. The simple CLI build does not issue/embed profiles automatically. Complete and verify that distribution path with full Xcode/signing configuration. See [App Group guidance](https://developer.apple.com/forums/thread/721701) and [command-line profiles](https://developer.apple.com/forums/thread/835305).

In Xcode, set `WORKBOARD_APP_GROUP_IDENTIFIER` and the actual team together. Plists, entitlements, and the service build step share it. macOS-only `TEAMID.` identifiers are not registered in the developer portal; configure Register App Groups appropriately.

The host uses external project files and local sockets and is currently not sandboxed. The widget is sandboxed with App Group permissions. App Store distribution is outside verified scope.

Sign the Rust service separately using `Resources/Service.entitlements`; host permissions do not automatically transfer to children. The CLI/installer-lock helper need no shared-data entitlement. Even a valid signature/declaration requires an actual successful container write.

## Earlier App Group failures

In the first environment, adding service entitlements and reinstalling still produced `Operation not permitted` for LaunchAgent shared writes. The same entitled service could write a new diagnostic JSON under terminal process responsibility, but an isolated, uniquely named LaunchAgent could not write even a fresh UUID filename. Diagnostic agents were removed, without changing the original service/snapshot. Terminal success does not prove LaunchAgent access.

That Mac had no valid signing certificate or service Team ID. `containermanagerd` rejected the group request based on signing/prefix conditions. `tccd` attributed access to the host and reported the changed ad-hoc cdhash did not match the prior requirement. During the October 15 check around 17:00, the default snapshot sequence was 20 while shared sequence remained 6. This did not establish App Group synchronization or desktop-widget completion. No ownership/ACL changes or privacy bypasses were used.

## Development-team signing and desktop widgets

Actual desktop behavior was later verified with full Xcode and a development-team certificate. Add an Apple ID in **Xcode Settings → Accounts**, then create an Apple Development certificate under **Manage Certificates…**. A free Personal Team is sufficient for this local use.

```sh
scripts/build-xcode.sh --team TEAMID
scripts/install-local.sh --start-service
```

Use `TEAMID.local.agentworkboard.shared`. This macOS-only prefix required no portal registration/profile in the verified environment. Automatic signing may contact Apple to check the account. The script checks app/widget/service teams and unregisters Xcode's build from LaunchServices. Installation terminates old widget-extension processes so replaced binaries stop rendering.

Observed on a second Mac with macOS 27 and Xcode 27:

| Check | Result |
| --- | --- |
| Command Line Tools widget | Even with team signing, chronod purged registration with `Requested to add extension, but purging instead because we shouldn't cache it`; an App Sandbox entitlement diagnostic preceded it. |
| Full Xcode widget | chronod launched it, read descriptors, and showed it in the gallery. Xcode adds SDK information, App Intents metadata, and debug permissions; the decisive difference was not isolated. |
| Service shared writes | Path-only access was silently denied by `kTCCServiceSystemPolicyAppDataDetailed`. Resolving the group container first allowed the same signed code to write. |
| Refresh while app stopped | A separately signed WidgetCenter helper was rejected with ChronoCoreErrorDomain. The containing app's `--reload-widgets` mode was accepted; service invocation reflected CLI changes in the widget. |

## Snapshots and refresh

The default derived file is `widget-snapshot.json` in the data directory. The app resolves its group container and configures the shared path. Startup environment `WORKBOARD_WIDGET_SNAPSHOT` and persistent `widget.configure` are distinct; an already running service does not inherit later environment changes. Verify saved configuration/shared output or restart with updated startup settings. Never create arbitrary Group Containers directories as a substitute for authorization.

Daily summary groups In progress, Due today, Completed today, and nonempty Needs review. App Intent heading buttons persist collapsed state in shared preferences. Date-only deadlines use the Mac's date; timed schedules use stored zones. Single views are also configurable.

Only DEBUG widgets allow development fallback with `WORKBOARD_WIDGET_ALLOW_DEV_FALLBACK=1` plus `WORKBOARD_WIDGET_SNAPSHOT` or `WORKBOARD_DATA_DIR`; sandbox path access must still be authorized. Release widgets ignore fallback paths.

Snapshots include schema, sequence, generation time, and task display data. Widgets filter/sort tasks, display last update, and mark data stale after 15 minutes. Missing/invalid files prompt the user to open the app. Reload requests do not guarantee immediate refresh because macOS controls scheduling.

## Automated checks

```sh
scripts/verify-widget.sh
# Also decode an actual service snapshot:
scripts/verify-widget.sh "/path/to/widget-snapshot.json"
python3 scripts/test-install.py
```

Installer checks use separate `/tmp` data/apps, short sockets, and unique service names. They do not change HOME or the default service. launchctl/LaunchServices are simulated, so these tests do not prove actual login registration. Service processes, SQLite, code signing, sockets, and install locking are real. Cover manual takeover/data preservation, managed updates, same-source installs, pre-start registration rollback, failed bootstrap recovery, failure after schema migration with new writes, foreign-service protection, and CLI lock waiting. The default fixture builds a minimal signed app bundle with real CLI/service executables; set `WORKBOARD_INSTALL_TEST_APP` to test a specific built app copy. This does not exercise the native GUI or actual login registration.

For isolated development use `--data-dir DIR --socket PATH --service-label local.agentworkboard.test.NAME --agent-dir DIR --log-dir DIR`; ordinary installs need no overrides. Do not overwrite the default group snapshot from an isolated board.

Widget checks compile AppIntent/static paths and validate JSON, filters, priorities, subtasks, deep links, staleness, incompatible schemas, daily sections, and collapsing. They check plist/entitlement syntax. Snapshots may contain extra task details; widgets read only required fields.

The first environment had Swift 6.3.3 and Command Line Tools with macOS SDK 28, without full Xcode. macOS 14 compilation/linking and project generation passed, but xcodebuild could not run. A second Mac with Xcode 27/Swift 6.4 initially exposed Swift 6 concurrency errors; marking static widget configuration `@MainActor` fixed them. Later personal-team-signed tests established the desktop results above.

`scripts/build-macos.sh --debug --skip-rust` produces a complete development bundle and checks nested signatures/plists. That alone proves neither installed-widget behavior nor external signing.

An earlier ad-hoc install on October 15 registered one extension in pluginkit and the `workboard:` scheme in LaunchServices, but chronod purged descriptor caches. That was insufficient proof of gallery visibility. Core board/CLI tests remain independent of widget registration.

`scripts/render-widget-previews.sh` draws the same widget UI into small/medium/large PNGs under `.build/widget-previews/`; medium cards fit side by side. These are layout checks, not WidgetKit-host evidence.

Verify on an actual installed Mac:

1. Gallery visibility and adding supported sizes. The second Mac verified the Xcode medium widget.
2. Shared JSON/task/time changes after CLI updates. Verified with the app stopped on the second Mac.
3. Task links opening app details. Verified there.
4. Stale state after stopping the service for 15 minutes. Not yet performed.
5. Correct login startup after signing out/in. Not yet performed.
6. Persistent widget view/accent settings. View changes and section collapsing were verified; accent changes were not.

## Native interaction tests

On a full-Xcode Mac, use XCUITest against real windows. One-time automation setup requires administrator rights and can be reversed with `disable-automationmode-without-authentication`.

```sh
sudo automationmodetool enable-automationmode-without-authentication
macos/Tests/run-ui-tests.sh
# Run one test:
macos/Tests/run-ui-tests.sh -only-testing:WorkboardAppUITests/WorkboardAppUITests/testTaskLinkOpensTaskDetail
```

Each test uses temporary data/socket and a separate `WORKBOARD_DEFAULTS_SUITE`, without touching the user board/preferences/widget files. The bundled CLI acts as the agent.

The runner:

- Uses local ad-hoc signing and removes App Group entitlements from test builds, which do not use them.
- Re-signs only the Xcode UI runner without its sandbox so launched CLI/service processes can create disposable boards.
- Temporarily selects the ABC input source because synthesized shortcuts depend on the active keyboard layout, then restores the original source.
- Unregisters Xcode's test app afterward so deep links continue opening the installed app.

Do not use the keyboard/mouse while test windows open and close. Result recordings include the whole screen, potentially other apps, and should not be shared. These tests do not establish desktop-widget behavior.

## Disk image and external distribution

```sh
scripts/create-dmg.sh
```

Create a DMG with the built app and an Applications link, then verify image integrity. External release additionally requires Developer ID signing, authorized App Groups, hardened-runtime checks, and Apple notarization. Local signing is not notarized distribution.
